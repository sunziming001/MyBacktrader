# 通达信二进制数据一律自研解析，第三方库仅作测试对照或字段映射来源

通达信的三种本地二进制格式——`.day` 日线、`gbbq` 权息事件、`vipdoc/cw` 财务数据——**一律自研解析**。第三方库只允许以两种受限方式参与：**开发期测试对照**（独立 oracle），或**字段映射表的来源**（限 MIT 许可、须注明出处）。绝不作为运行期依赖，绝不拷贝代码。

## 各格式的决策与其理由

- **`.day`**：定长 32 字节记录，约 50 行。自研无争议。
- **`gbbq`**：`4 字节计数 + N × 29 字节`，每条记录**前 24 字节为 16 轮 DES 类加密**（内嵌 4176 字节密钥表，**非 XOR**），后 5 字节明文。自研理由是**法律**：`pytdx` 仓库**无任何许可证文件**（默认保留所有权利），拷贝其解密代码存在明确瑕疵，且该库自 2019 年归档。自研无法律问题——**这是通达信的文件格式，不是 pytdx 的智慧财产**。`pytdx` 反被用作**测试对照**。
- **`vipdoc/cw`**：`20 字节头 + nstk × 11 字节索引 + nstk × 2336 字节块`（584 个 `float32`），**明文无加密**，约 40 行。自研理由是**成本与验证**：本项目只需约 3–5 个字段（公告日 float 313、营业收入 float 73、净利润 float 94/95），而 `mootdx` / `mootdx2` 唯一值钱的是那 584 个字段的中文映射表——**我们用不到**；且它们读本地文件这一点**未经实测**，其 `mootdx.utils.gpcw()` 已知是坏的（硬编码 264 个 float、只返回第一只股票）。

**刻意说明**：`mootdx` 与 `mootdx2` 均为 **MIT**，法律上完全可用。此处仍选自研，**不是**因为它们不可用，而是「需要的少 + 结构简单 + 依赖有验证缺口」。**若将来要铺开 50 个以上基本面因子**，那张 584 字段映射表就从负担变成资产，届时**应当重新评估**改用 `mootdx`——本 ADR 记录的是当下的取舍，不是永久禁令。

## 暂不逆向 `gp{sh,sz,bj}NNNNNN.dat`

`vipdoc/cw` 中占 62%（1.5 GB）的 8,969 个 `gpXX*.dat` 是 13 字节定长记录 `[u8 tag][u32 date][f32 a][f32 b]`，约 45 条带 tag 的序列拼接，部分 tag 恰好截断在 2000 个日频点。**tag 语义未确认，且全网无开源解析器。**

一期不逆向它：其结构特征指向「每日个股指标」（市盈率、市净率、换手率、市值之类），若属实会直接提供市值与估值；但**全网无解析器这一事实本身**就是产出不确定的证据，不值得挂在关键路径上。一期改用**已解开的 `gbbq` 类别 5 股本 × 价格**自算市值与估值，其输入全部已就位、不需任何新未知。

`gpXX` 作为**已存在于硬盘上的已知资产**记入路线图。待市值算法跑通后，两者可**互相校验**——届时逆向它从「猜测」变为「对账」，难度低得多。

## Consequences

本项目对通达信格式的知识**完全内化**，不依赖任何第三方解析器，也就没有版本升级、许可证、维护状态的风险。代价是三种格式的正确性全部由我们自证——因此 `.day` 的格式假设、`gbbq` 的解密结果、`cw` 的字段索引**都必须有测试覆盖**，`gbbq` 与 `cw` 更要与独立 oracle（`pytdx`）对账。

## 修订：`gpXX*.dat` 的布局已解，语义仍只能对账（票据 #50）

上面「暂不逆向」一节的**布局描述已经实现并验证**（`mbt.data.gp`），但**编号语义**依然没有解——而且查清楚了为什么解不了。

**布局：在全部真实文件上成立。**

- 本机 8,976 个 `gp{sh,sz,bj}*.dat`，**长度无一例外都是 13 的整数倍**；共 245,470 个 id 段、
  125,689,706 条记录。
- 「一个 id 一段连续记录」在全部 8,976 个文件上**零反例**；段内日期非升序 168 例，而这 168 例
  **全部**由日期字段本身残缺引起（值形如 `201408`，即缺了「日」的 `YYYYMM`），读出的序列仍是
  严格升序。
- 解不出的日期共 695 条（占 0.0006%），其中恰为 0 的 341 条——**极少**，跳过即可，不能因此报错。

**编号语义：本机取不到那张表。** 查过的地方与结论：

- `TCalc.dll`（公式计算库）里只有公式帮助原文：``GPONEDAT(ID),ID为数据编号``，并把它归为
  「股票的**单个数据（非序列）**」；「序列」那一族叫 `GPJYVALUE` / `FINVALUE`。
- `vipdoc/cw/gpcw.txt`、`gpszsh.txt`、`gpszsh.local` 是**下载清单**（文件名 + MD5 + 字节数），
  不是字段表；`TCFMod.dat` 只是版本与文件指纹清单。
- 全安装目录搜不到任何 `编号 → 字段名` 的清单。故语义**不能靠猜**（本 ADR 的自证要求），
  只能对账。

**一个 id 已经对上账：`id = 30` 是除权除息日。** 这正是本 ADR 预判的那条路——「待市值算法跑通后，
两者可互相校验」：拿 `gbbq`（另一个自研解析器，读的是完全不同的文件族、走另一套解码）去对。

- `sh600000` 的 26 个日期**全部**落在 `gbbq` 的除权除息事件里；
- 两边**只差 2006-05-12 一天**，而那天是股改对价送股——**不除权**（见 `mbt.data.dilution`），
  故不进「除权除息」这一栏。差额恰好是这一天，说明 id 30 的口径是「除权除息」而非「一切股本变动」。

**id 是跨标的稳定的字段码**，故这张编号表一旦拿到，全市场通用——这也让「拿到表之后值得再投入」
这件事有了依据。

**时点纪律在日频 id 上做不到，已登记为不可回溯缺口。** 见 ADR-0006 的修订。

**两个操作上的坑，记下来：**

- `gp*.dat` 这个通配符会**连带匹配到 `gpcw*.dat`**（`gp` + `cw…`）。按它做全量统计会把
  `gpcw` 的头部结构与百万级记录算进来，得到「46% 的日期解不出」这种假结论。凡是按前缀找
  gp 文件，一律写 `gpsh*` / `gpsz*` / `gpbj*`。
- 本 ADR 开头写的「8,969 个 `gpXX*.dat`」与本机实测的 8,976 有出入，以实测为准（文件随客户端
  更新而增减）。

**仍待确认的前提**：`gpXX*.dat` 是一个按 id 存**序列**的文件，而 `TCalc.dll` 的帮助把
`GPONEDAT` 归为「**单个数据（非序列）**」。两者未必对不上（序列文件同样可以只取最新一条），
但「`gp*.dat` 就是 `GPONEDAT` 的数据源」这个前提**尚未被证实**，接手时先验这一条。
