# 选股的质检窗口取「评估日往前 N 根」，不再覆盖全部历史

`mbt screen` 的**质检窗口**（:func:`mbt.data.dilution.resolve_dilution` 的稀释判定 + :func:`mbt.data.anomaly.require_no_anomalies` 的越界检查）从「全部历史」改为「**评估日往前 1300 根**」（`--quality-bars`，0 表示不限制）。修复前，全市场 **1,028 只（17.4%）** 的标的仅因十几年以前的越界或除权判定而被拒之门外——包括 `sh600547`，而它在 2026-09-15 过得了全部 8 道 B1 门。

## 症状：用 2006 年的数据否决 2026 年的选股

`sh600547`（山东黄金）在三个口径下的结果：

| 口径 | 结果 |
|---|---|
| 不给 `start` = **`mbt screen` / `b1_daily.bat`** | ✗ 被拒：`在 2006-03-31 的除权事件判不动（两个假说的带都落不进）` |
| `start=2015-08-01` = `mbt backtest` | ✓ 加载成功 |
| `start=2020-01-01` | ✓ 加载成功 |

而它在 2026-09-15 的八门读数全部合格（收盘 774.05 / 白线 805.45 / 黄线 744.63、**J = 0.63**、放量 2.53、缩量 0.303、PE 18.5、PE 百分位 3.1%），是该标的**历史上唯一**的全通过日。

## 根因：区间只补了一半

`load_market_data` 的文档早就写明「越界检查**只在这个区间内做**……区间之外的数据本来就不交易」，`mbt backtest` 因此传 `--start`（默认 `DEFAULT_START`）。而 `mbt screen` **没有 `--start`**——它的参数表里只有 `--as-of`，代码注释写着：

> 选股只看评估日及之前，故越界校验也只做到那一天（理由见 backtest 那条注释）。

**上界补了，下界没有。** 于是质检覆盖「从最早一根到评估日」，历史上任何一处说不清的日子都会让整只标的被拒。这不是新增的缺陷——ADR-0005 落地时选股与回测就分了两条路，只是选股那条一直只有上界。

## 为什么不直接用 `--start`

选股的评估日在**取数时还没定出来**：`--as-of` 可省，默认取「最近一个齐全的交易日」（理由见 `_resolve_as_of`：本地数据末根常是半截的），而那要读数据才知道。**先有数据才能定日期，先有日期才能定区间**——循环。故这里用「相对窗口末端的根数」，它不需要知道日期；而 `end=--as-of` 已经把窗口上界定住，于是「最后 N 根」自动就是「评估日往前 N 根」。

## 代价：池子大了，选股更慢

救回 1,028 只的代价是筛选阶段变重，而新增的多是**长历史老股**（2006 年前后上市，K 线数是新股的好几倍）。同 1,200 只标的的 A/B：旧口径加载 467 只、新口径 **1,003 只**（2.15 倍），筛选量随之上去。实测全市场一次选股从约 **16 分钟**升到 **一小时以上**（一次 63 分钟的运行被外部信号中止，未跑完；故没有「一次完整选股的端到端用时」这个数，只有上面的跳过率与 A/B）。**这一句已过时**——今天同一命令约 10 分钟，见文末「修订」。若要压这一项，得看 `top_calm`（A/B 里单项 44 秒）那条的算法，不在这条 ADR 的范围里。

## 决策

**1. 新增 `--quality-bars`（默认 1300），把质检窗口收窄到「评估日往前 N 根」。** 两处检查同时受益：稀释判定与越界检查吃的都是同一个 `window`，故只改一处。**回测不传这一项**——它有 `--start`，本来就该用它把窗口定准。

**2. 取 `N + 1` 根，不是 `N` 根。** 与 `_window_of` 同一个理由：限价带与稀释判定都要用**前一根**算，窗口首根若没有基数，它上面的跳空判不出来。多要一根作基数后，「最后 N 根」里的每一根都真的被查过。这一点有变异检查钉住（去掉 `+ 1`，两条测试变红）。

**3. 1300 这个数由「最深回看」定，不由收益定。** 它必须盖过任何规则的回看，否则被检查的区间比用到的数据还短，检查就漏了。最深的一处是估值那条 `pe_percentile` 的 `DEFAULT_WINDOW = 1000` 根，故取 1000 加约三成余量。规则表变了、回看变长了，这个数要跟着调。

**4. `quality_bars=None`（不给）行为完全不变**，即检查覆盖整个 `[start, end]`。既有调用方（含 `b1_lib` 那条研究管线、`b1_run.py`）不受影响。

**5. 一处必须写明的影响**：窗口之外的权息事件会被 `resolve_dilution` 记为 `OUTSIDE_SERIES` 并**原样保留**（判定为「落在序列之外，无从谈起」），故那些事件的稀释成分不再被置零。**对选股无影响**（选股用的是窗口内的行情，且 B1 的 PE 两条读的是原始价），但这是「回测不要传这一项」的第二个理由。

## Considered Options

- **给 `mbt screen` 也加 `--start`，由 `--as-of` 反推**。最贴近回测的语义，但要先解决「取数前无法知道评估日」——须新增一次「扫各 `.day` 文件末根日期」的预读，才能把 `as_of` 定下来。**本轮不取**：代价是一次新的数据层扫描 + 一套新测试，而 `--quality-bars` 达到同一目的且不需要知道日期。若将来 `latest_complete_day` 需要在取数前可用（例如要按日期过滤标的），那条路还是要走。
- **无条件豁免「序列前 5 根」**。见 ADR-0013 的同名否决项：那是位置启发式，会把核准制老股的第 2~5 根一并放过。本 ADR 不碰那一类。
- **放宽 30% 跳过率红线**。只把门槛挪过去，且每上一只新股就更紧。**否决**：ADR-0013 已就同一问题否决过一次。
- **把 `anomaly_bars` 与稀释判定分两个开关**。写这套改动时先做的是「只收窄越界检查」，而实测 `sh600547` **仍被拒**——拦它的是稀释判定。两个开关会让人以为可以分别调，而它们吃的本就是同一个窗口。**否决**：一个窗口，一个开关。

## Consequences

- **候选池会变大**：救回的 1,028 只（集中在 2006 年前后就有行情的老股）从此进入选股范围。**此前所有全市场选股结论都是在少了这批标的的池子上算的**——包括 2026-09-15 那份逐日候选统计（`b1_daily_candidates.csv`）与 ADR-0012 那批对照。这不是错误，但那些数字的适用范围要照此理解；要推广到全市场就得重跑。
- **`mbt screen` 的跳过率 25.0% → 7.6%**，`b1_daily.bat` 越过 30% 红线的余量从「刚好越不过」变成「绰绰有余」，且不再需要靠排除北交所来绕（见下）。
- **`b1_daily.bat` 里那处 `EXTRA=--boards 主板,创业板,科创板` 的绕行已还原为空。** 它是在本 ADR 之前为了压跳过率加的，而它**同时改掉了股票池**——与 ADR-0012 那批结论的口径不一致（该文件自己的注释正警告过这类漂移），也踩了它自己那条「纯 ASCII」的契约（4 项测试因此红）。跳过率下来之后它没有必要存在。
- **ADR-0013 与本法是两件独立的事**，缺一不可：ADR-0013 修的是「上市初期不设涨跌幅」（约 811 只，用上市日豁免），本法修的是「窗口之外的越界与除权判定」（1,028 只，用窗口收窄）。
- **`anomaly.py` 的「报错让人看」定位不变**：窗口**之内**的越界照旧报错，坏数据仍然拦。收窄的是「看多远」，不是「要不要看」。

## 修订：两处读数已不可复现（2026-09-17，票据 #71）

本 ADR 的两个数字——跳过率 **25.0% → 7.6%**、用时**「一小时以上」**——今天都对不上。两个原因都与本 ADR 的决策无关（决策本身不变、实现未改），但后面的读者需要知道，否则会拿它们当基线。

**一、本地行情被重下过，现在只剩 2015 年起的十年。** 全市场 9,731 个 `.day` 里只有 **50 只**首根早于 2015；`sh600000`（1999 上市）、`sh600547`、`sz000001`、`sh601398`、`sh600028` 的首根**全都是 2015-01-05**，是同一批下载的印记（`--start` 的默认值 `2015-08-01` 正是这次重下的目标区间，故**回测侧无损**）。

后果是**本 ADR 的动机在当前数据上复现不出来**：`sh600547` 那根 2006-03-31 的 K 线已不在序列里，该年的除权事件因此落在序列之外、根本不被判定。实测 `--quality-bars 0`（即 `quality_bars=None`，本 ADR 之前的旧口径）也照样加载 `sh600547`。「窗口之外不判」这个机制没有变、也仍然正确（数据若再下深一档，它立刻又需要），只是今天**已经没有「远古越界」可救**——下面那张表里的 99 只都是 2015 年之后那一段的。

**二、「一小时以上」不是一次完成的测量。** 它来自一次 63 分钟被中止的运行（「代价」一节已注明「未跑完」）。今天同一条命令跑通全程，两次实测：**干净的一次 279.3s ≈ 4.7 分钟**，另一次 587.8s——那一次的前四分钟机器上另有一个全盘扫描在抢磁盘（取数 252.7s，而干净那次 131.5s）。**该按「约 5–10 分钟」读，不是「一小时以上」。** 之后的性能批次（取数 8.5×、估值 5×、`volume_pattern` 前缀和、`swings` 16~18×）把这几个阶段压下去了。同数据下的加载量 2.15 倍仍然成立，该读作「同样数据下质检工作量增加」，不是「一次选股要一小时」。

## 修订：面板日历也取「评估日往前 N 根」（2026-09-18，票据 #78）

上面那条修的是**查多远**（质检窗口），这一条修的是**面板有多高**（算读数用的那张表）。两件事的窗口不同源：质检窗口是「检查哪一段」，面板日历是「整个信号层要算多少格」。

现象：`b1_daily.bat` 偶发失败，五次里跑挂一两次，只留一行「错误：选股失败——MemoryError」。根因不是代码，是**机器当时的余量**——同一份数据、同一条命令，余量够就过、不够就死。

**面板高得没有道理。** 本地 5,377 只标的中只有 **45 只（0.84%）**首根早于 2015，而并集日历由它们一直撑到 1992-03-30：于是面板是 **8,387 行**，其中 2015 年之前那几千行几乎是空的（那 45 只以外一个标的值都没有），却按满表收费。规则真正看的最深处是 `pe_percentile` 的 1,000 个交易日。12 GB 上限下它死在一次 `Unable to allocate 344. MiB for an array with shape (8387, 5377) and data type float64`——正是这张满表的一格一数。

### 实测（同一台机器、同一条命令，只差面板行数）

```
===============  =============  ==============
                全长 8387 行   末端 1301 行
===============  =============  ==============
12 GB 下退出码   1              0
提交峰值         13.91 GB       4.80 GB
墙钟             276s           178s
候选             四只           同四只、同序
===============  =============  ==============
```

全长那个 13.91 GB 是在 64 GB 上限下量到的真实峰值——在 12 GB 上限下它死在 12.02 GB，那只是撞线瞬间的高水位。省下来的全在信号层（后复权 21.3s → 7.5s，估值 26.8s → 12.2s），取数两边同一量级（85.0s / 92.4s，它跑在截断之前，不受这个开关影响）。这组数字量在**只含本改动**的那棵树上。

**与「逐标的取末端 N 根」的区别就是本节的重点**：那样切只从 8,387 行降到 6,792 行（每只标的自己早年的行还在，并集照样高），故本条 ADR 切的是**日历**——并集日历切到末端 N 行，各标的只取落在其中的行。

### 为什么敢切（实测，不是推算）

- **数值**：切到 1,301 行后，从第 W 行起与新起点无关。实测 `kdj` W=125、`white_line` 226、`atr` 585、`swings` 与 `top_calm` 812。唯一做不到逐位的是**黄线**——它是若干条移动平均的等权均值，累加起点换了末位就变，实测最大相对差 5.7e-16；它**永远不逐位相同**，但读它的两道门（`trend`、`not_below_the_line`）**翻转 0 / 5,377**。判据的两个档次（逐位 / 末位级差加零翻转）沿用 ADR-0015 已有的规格，两边都报。
- **拐点能有多老**：全场最大「谷底距评估日的根数」488、峰值 348；参与排名的那批（八门通过的 4 只 + 分数前 50）最大 184。没有一只超过 1,301。
- **评估日那一格**：5,377 只标的的读数逐个比过，候选名单与全长**逐字、同序**。

### 决策

**6. 新增 `--panel-bars`（默认 `0` = 不截断），把面板日历切到「评估日往前 N 根」。** 只有 `mbt screen` 收这个开关——回测的区间由 `--start`/`--end` 给，且它逐日推进、不需要一个末端窗口；把这个开关也开给回测只会让人以为它有同样的内存效果。默认关是刻意的：一次证据规格很重的改动不该进所有人的默认路径，故由 `b1_daily.bat` 显式打开。

**7. `N = 1301`**，与决策 3 同一个推导：最深回看是 `pe_percentile` 的 1,000 根，加三成余量再加 1（那一根作基数，同决策 2）。

**8. 窗口短于 1,000 根时**拒绝运行**，不是警告**，且**看的是「实际会用到多少历史」，不是
「请求了多少」**。闸门比的是 ``min(请求根数, 评估日身后的可得行数)`` 与 1,000 的大小，故两种
情形都拦得住：请求的根数本身太少（``--panel-bars 999``），以及数据不够长以致切不动、评估日
身后本来就只有那么几行（短历史 + 大 N）。两者的后果相同——``pe_percentile`` 在历史不足窗口时
照常给值（``min_periods=1``），只是那个值算在更短的窗口上，**不报错、只让名单悄悄变**：实测
面板取 1,000 行时评估日的读数与全长逐位相同，取 **999** 行则有 **81 只**标的的读数不同，
最大一处从 0.815 变成 0.029（``sh600114``）。差一格是断崖，故它是闸门。

**9. 「历史本来就比 N 短」不算错误——但要同时够深。** 切不动就不切，继续跑，只如实说
「未截断」（决策 8 已把「短到影响读数」那一类拦掉了）。这一条只覆盖「短到切不动、但没短到
影响读数」，不是「短了就一律放行」；把两个条件混成一个，决策 8 在「数据太短以致切不动」那一
格上就永远不触发——**那一格是本条最容易漏的地方**，`test_the_gate_also_fires_when_the_data_is_too_short_to_cut`
把它钉住。

**10. `panel_bars`（请求）与 `panel_rows`（实际）都记进 `run.json`**。同一份名单按 1,301 根
还是 1,000 根历史算出来的，看 CSV 分不出来。只记请求值不够——数据不够长时它记的是一个没发生
的动作。两者的差还顺带说明了那次到底切没切。

**11. 估值与前瞻口径也随窗口收窄。** 喂估值的那份行情就是面板依据的那一份（原始价视图），
故 ``选用PE`` 的百分位与 `valuation_caliber.symbols` 都算在窗口上。这不只是省内存：百分位
**本来**就该在「被验证过够深的那段历史」上算，而够不够深由决策 8 的闸门回答。等值性由评估日
读数的逐位比对与候选名单的逐字同序保证（见上「实测」）。窗口内没有 K 线的标的会掉出这次
估值，且**会被记进产物的 `skipped`**——`_write_screen_artifacts` 收的是截断之后的那份取数
结果，故两段跳过都在。

### 一处与最初设想不同的地方：评估日与股票池都得在截断**之前**定

原计划是「评估日定完、复权之前」切。落到代码里发现这个位置不存在，且不止是位置问题：

- **评估日**是喂面板算出来的（`_resolve_as_of` → `mbt.data.panel.latest_complete_day`），而面板在**后复权之后**才组装。故现在先用一份**只含 `close` 一栏**的临时面板把评估日问出来（那个判据看的就是收盘价的覆盖数），再切。
- **股票池**的次新股门槛在没有 `--master` 时数的是「**截至当日的累计根数**」（`mbt.universe`）。窗口一短，累计就从新起点数起，长期停牌的标的会静默掉出池子——而 `b1_daily.bat` 里 `EXTRA=` 是空的，走的正是这条近似口径。故 `build_universe` 提到截断之前（它只用得到 `symbol` 与 `prices`，与复权无关，故这一步是行为保持的搬动），股票池于是与不截断时逐格相同。

顺带量了这个风险有多大：窗口内不足 60 根的标的有 **47 只**，而**这 47 只在全长口径下也不足 60 根**（都是真次新股，本就该被排除）——即这条口径改动今天影响 **0 只**。搬动不是为了修一个正在发生的错，是为了拆掉这份脆弱：它今天凑巧为零，不是结构保证。

### 夹具进仓

本条的判据靠一套夹具（`tools/oom_loop.py`）：用 Windows Job Object 给进程钉一个提交上限，再跑与 `b1_daily.bat`**同一条**命令，让偶发失败变成每次都在同一个地方死。它带一个 `--selftest`，确认上限真的生效——**这一步不是可选的**：`JOB_OBJECT_LIMIT_JOB_MEMORY` 写成 `0x2000`（那是 `KILL_ON_JOB_CLOSE`）的表现是上限看着设上了、`JobMemoryLimit` 却被清零，于是一路吃满内存不报错，而「没红」会被读成「修好了」。

它不再住 `tmp/`：这套夹具**已经丢过一次**（本条的证据是重建出来的）。同一个坑仓库里踩过两回——ADR-0015 引作复现入口的 `smooth_dump_or_compare.py` 住在 gitignore 的 `.scratch/` 下，后来全盘搜过，已经不在了。故它进仓，但**不进测试套件**（依赖 Windows 的 Job Object 与 `GetProcessMemoryInfo`，换机器就未必跑得动，手动跑）。

### 仍未动的两处

- **复权那一步的内部复制**：`mbt.data.market` 里有两处整表复制，与面板多高无关，切完仍是同样比例的开销。不在本条范围。
- **面板数组重写**：把「字段 → 标的宽表」的映射换成一块连续数组，能再省一批。也不在。

## 修订：闸门改按**规则自己声明**的深度比（2026-09-19，票据 #86）

决策 8 那道的判据是「小于 `PANEL_WARMUP_BARS = 1000` 即拒跑」，而 1000 取的是**所有规则里最深的那处**（`pe_percentile`）。当初刻意这么做，理由原话是「宁可让一个不需要长历史的规则多要一点，也不要为每条规则维护一份『它最深看多远』的表」。

那个理由**今天不成立了**：第二张表不必维护——**数就写在规则旁边**。砖型（票据 #85）的读数只由三层递推平滑算出，最慢那层的记忆按 ``(5/6)^t`` 衰减，它要的历史比 1000 根浅一个数量级，而 1000 根这道闸门让它**永远降不下去**（`--panel-bars 200` 会被直接拒跑，于是面板窗口下不来、本条省的内存也拿不回来）。

因此改判据，不改闸门的性质：

**12. 新增 `Screen.lookback_bars`（默认 `None`），闸门比的是 `rules.lookback_bars or PANEL_WARMUP_BARS`。** `None` 的语义是「本规则不额外要求」，此时仍按 1000——**故所有既有规则逐格不变**（有一条测试专门钉住这一点：只有「按声明比」而无「不声明的照旧」，读起来就像闸门被拆了）。报错里要写明那个数**是谁定的**（「这条规则自己声明的」还是「回退来的」），否则读者不知道 100 这个数从哪来。

**13. 砖型声明 100 根，依据是量出来的。** 取真实日线切片逐次截到末端 N 根重算，末位读数与全长之差：N=10 时 3.78e-01、20 时 1.13e-01、30 时 3.08e-02、40 时 1.54e-03、**50 起逐位相同**（`(5/6)^N` 的理论界在 50 上是 1.1e-04）。取 100 是留一倍余量。`--panel-bars 200` 是推荐的每日取值（在声明的 100 之上再留一倍）。

**14. 同机 A/B（`tools/oom_loop.py --screen brick`，两次相隔几分钟、选出同一批 667 只）**：

| 面板窗口 | 峰值提交 | 墙钟 | 取数 | 复权 | 砖型那几项 |
|---|---|---|---|---|---|
| 1301 根 | 3.99 GB | 123s | 108.0s | 9.3s | 4.3s |
| **200 根** | **3.41 GB** | 871s | 844.9s | 24.3s | 0.7s |

**内存那两列可比，墙钟不可比**——后一次跑在我自己占着机器的时候，取数从 108s 涨到 845s（同一份代码在同一台机器上差这么多，README 已写明这个量级）。故照纪律**只用内存那一对**：截断 1301 → 200 根省下 **0.58 GB（14.5%）**，而两次的成功候选**逐只相同**。

省得比本条当初设想的少：本 ADR 正文里那次是 1301 根对**全长 8387 行**，落差大；而 1301 到 200 这一段，`取数` 与 `复权` 那两块（与面板多高无关）已经占了内存的大头。**3.41 GB 是这一段的实测地板**，要再往下压得动那两块，不在本条范围。

**这一处修订的代价**：闸门现在读的是一个**可被规则写错**的数。写小了会让读数静默算在更短的历史上——而那道闸门存在的全部意义就是拦这个。故声明值必须附带**它从哪来**（`BRICK_LOOKBACK_BARS` 的 docstring 里就是那张实测表），而不是一个光秃秃的常数。
